# Φύλακας: ό,τι σκόνταψε στο Make

Οταν ένα σενάριο του Make αποτύχει σε ένα bundle (κενό email πελάτη, έντυπο
χωρίς PDF, σφάλμα του Gemini), το bundle παρκάρει στα **incomplete
executions** και το σενάριο συνεχίζει κανονικά. Αυτό είναι σκόπιμο, χωρίς
DLQ μια κακή υποβολή θα κατέβαζε όλα τα έντυπα (βλ.
[make-scenarios.md](make-scenarios.md)), **αλλά το Make δεν ειδοποιεί
κανέναν**. Στις 31/07/2026 βρέθηκαν εννιά ανεπίλυτα, το παλαιότερο
δεκαπέντε ημερών: μια **εντολή ανάθεσης της 17/07 που δεν έφτασε ποτέ στον
πελάτη** και κανείς δεν το πήρε είδηση.

```
cron Worker (κάθε 15') ──μία φορά την ημέρα, μετά τις 08:00──▶ Make API
   worker/lib/dlq-watch.mjs                                 /scenarios (dlqCount)
                                                            /dlqs?scenarioId=…
                                                            /dlqs/<id>/bundle
                                    │ μόνο αν υπάρχει κάτι
                                    ▼
                         POST MAKE_DLQ_WEBHOOK ──▶ σενάριο 6775485 ──▶ email info@
                                                   (webhook → email)      cc panos@
```

## Γιατί έτσι

- **Ο έλεγχος ζει στον Worker, όχι σε σενάριο Make.** Το Make API θέλει
  token, και το token θα κατέληγε μέσα στο blueprint, δηλαδή στο git.
  Ετσι το μυστικό μένει secret του Worker και το σενάριο είναι δύο modules
  χωρίς τίποτα ευαίσθητο μέσα του.
- **Μία φορά την ημέρα, όχι σε κάθε tick.** Το ίδιο το module κρατάει την
  ημερομηνία της τελευταίας εκτέλεσης στο KV (`dlq-watch:last-run`) και τη
  γράφει **πριν** στείλει, ώστε δύο ταυτόχρονα cron ticks να μη στείλουν
  δύο email. Μια χαμένη μέρα είναι ασήμαντη, ένα διπλό email όχι.
- **Σιωπή όταν όλα είναι καλά.** Email φεύγει μόνο όταν `count > 0`, και το
  φίλτρο υπάρχει και στο σενάριο. Ενα email που έρχεται κάθε μέρα «όλα
  εντάξει» παύει να διαβάζεται μέσα σε μια βδομάδα.
- **Ξαναέρχεται μέχρι να λυθεί.** Το DLQ δεν αδειάζει μόνο του, οπότε η
  ίδια εκκρεμότητα ξαναγράφεται αύριο. Το email το λέει ρητά, ώστε να μη
  φαίνεται σαν νέο συμβάν.

## Το email

Γράφεται για τη **γραμματεία** ([manual-site.md](manual-site.md): μηδέν
τεχνικά), όχι για προγραμματιστή. Κάθε γραμμή έχει τρία πράγματα: τι είναι
σε ανθρώπινη γλώσσα, πότε έγινε (με «πριν Χ ημέρες»), και **τι κάνουμε**.
Η μετάφραση «σενάριο → τι είναι + τι κάνουμε» ζει στον πίνακα `SCENARIOS`
του [../worker/lib/dlq-watch.mjs](../worker/lib/dlq-watch.mjs). **Νέο
σενάριο στο Make σημαίνει νέα γραμμή εκεί**, αλλιώς η γραμματεία παίρνει το
γενικό «ειδοποίησε τον Πάνο», που είναι σωστό αλλά άχρηστο.

Για τα έντυπα ανοίγει και το ίδιο το bundle (`/dlqs/<id>/bundle`), ώστε να
φαίνεται **ποιο έντυπο και ποιος πελάτης**, όχι μόνο «κάτι στα Εντυπα».
Ανοίγουν το πολύ `MAX_DETAIL` bundles ανά email.

## Config

| | |
|---|---|
| `MAKE_API_TOKEN` | secret. Make API token, χρησιμοποιείται μόνο για ανάγνωση σεναρίων και DLQ. |
| `MAKE_DLQ_WEBHOOK` | secret. Το hook του σεναρίου 6775485 (το URL είναι το credential). |
| `MAKE_TEAM_ID`, `MAKE_ZONE` | vars στο `wrangler.toml`, δημόσια αναγνωριστικά. |

Χωρίς token ή webhook ο φύλακας **μένει σιωπηλός** και δεν ρίχνει τον cron
του feed (τρέχει σε δικό του `waitUntil` με catch).

## Δοκιμή

```
GET /api/dlq-report?key=<WEBHOOK_KEY>              # JSON: count, subject, html
GET /api/dlq-report?key=<WEBHOOK_KEY>&format=html  # το email στον browser
```

Θέλει κλειδί επειδή το report γράφει **ονόματα πελατών**. Χωρίς σωστό
κλειδί γυρίζει 404, όχι 401, ώστε να μην αποκαλύπτει καν ότι υπάρχει.
Ο έλεγχος δεν κοστίζει τίποτα (μόνο κλήσεις στο Make API) και δεν αλλάζει
κατάσταση, οπότε τρέχει άφοβα όσες φορές θέλεις.

## Τι ΔΕΝ πιάνει

- **Email που παραδόθηκε αλλά έπεσε στα ανεπιθύμητα.** Κανένα σύστημα δεν
  το ξέρει αυτό.
- **Email που απορρίφθηκε από τον παραλήπτη** (λάθος διεύθυνση, γεμάτο
  mailbox). Αυτό δεν είναι σφάλμα του Make, το σενάριο τελειώνει επιτυχώς.
  Το πιάνει το bounce του Zoho, που γυρίζει στο `info@` ως «Undelivered
  Mail Returned to Sender» (κάρτα στο εγχειρίδιο, [manual/emails.html](../manual/emails.html)).
- **Σενάριο απενεργοποιημένο ή σβησμένο.** Ο φύλακας βλέπει μόνο bundles
  που σκόνταψαν, όχι σενάρια που δεν έτρεξαν ποτέ.

## Το ξεκαθάρισμα του DLQ

Το Make **δεν έχει «σήμανση ως τακτοποιημένο»**: ένα bundle γίνεται
`resolved` μόνο με επιτυχημένο retry, αλλιώς σβήνεται. Retry σε παλιό
bundle **ξαναστέλνει πραγματικά email**, οπότε δεν γίνεται στα τυφλά.

Από το UI: σενάριο → *Incomplete executions* → επιλογή → Delete.
Από το API (χρήσιμο για μαζικό καθάρισμα δοκιμών):

```bash
# τι υπάρχει
curl -H "Authorization: Token $MAKE_API_TOKEN" \
  "https://eu1.make.com/api/v2/dlqs?teamId=2060918&scenarioId=<id>"
# τι είναι το καθένα (payload του webhook)
curl -H "Authorization: Token $MAKE_API_TOKEN" \
  "https://eu1.make.com/api/v2/dlqs/<dlqId>/bundle?teamId=2060918"
# διαγραφή, μία μία, ΜΗ ΑΝΑΣΤΡΕΨΙΜΗ
curl -X DELETE -H "Authorization: Token $MAKE_API_TOKEN" \
  "https://eu1.make.com/api/v2/dlqs/<dlqId>?teamId=2060918"
```

**Πάντα διάβασε το bundle πριν σβήσεις.** Στο ξεκαθάρισμα της 31/07/2026
(οκτώ bundles του photo pipeline) τα επτά είχαν ψεύτικο `batch_id` και
κωδικό ακινήτου `TEST`, αλλά το όγδοο αφορούσε **αληθινό ακίνητο**
(`2400005`). Σβήστηκε κι αυτό μόνο αφού φάνηκε ότι είχε σκοντάψει σε
σφάλμα διαμόρφωσης του module (`Missing value of required parameter
'stopOnHttpError'`), όχι στα δεδομένα, και ότι οι δοκιμές λίγα λεπτά
αργότερα είχαν πετύχει. Ο κωδικός ακινήτου μέσα στο payload είναι ο
γρήγορος τρόπος να ξεχωρίσεις δοκιμή από πραγματική δουλειά.
