# Νέα ακίνητα σε ζητήσεις — digest στη γραμματεία

Κάθε ζήτηση στο EstatePrime έχει ένα tab **«Ακίνητα»** όπου το CRM κρεμάει τα
ακίνητα που ταιριάζουν με τα κριτήριά της. Κάθε ματσάρισμα ξεκινά σε κατάσταση
**«Νέο»** και ο άνθρωπος το κάνει **«Προτεινόμενο»** ή **«Απορριφθέν»**. Το CRM
**δεν ειδοποιεί κανέναν** γι' αυτά — κάθονται εκεί μέχρι να τα δει κάποιος.

Αυτό το εργαλείο σαρώνει όλες τις ενεργές ζητήσεις και στέλνει ένα
συγκεντρωτικό email με ό,τι είναι ακόμη «Νέο».

```
tools/crm-request-matchings.mjs
  │  GET /api/requests            (Basic auth)      → ενεργές ζητήσεις
  │  POST /listings ×N            (session cookie)  → τα «Νέα» ανά ζήτηση
  │  GET /api/contacts/{id}       (Basic auth)      → όνομα + τηλέφωνο
  ▼
Make hook ──► Zoho ──► info@four-walls.gr (cc manos@, panos@)
```

## Γιατί δεν γίνεται από τον Worker

Τα ματσαρίσματα **δεν υπάρχουν στο public API**. Το `GET /api/requests` γυρίζει
μόνο τα κριτήρια της ζήτησης· η κατάσταση «Νέο/Προτεινόμενο/Απορριφθέν» ζει
πίσω από το εσωτερικό `POST /listings` που θέλει **session cookie** — άρα ο
έλεγχος τρέχει τοπικά μέσα από τον αφιερωμένο Edge στο `:9222`
([edge-cdp-automation]), όχι στο Cloudflare. Το πλήρες field map είναι στο
[estateprime-api.md](estateprime-api.md) («Ματσαρίσματα ζήτησης»).

Θα μπορούσαμε να υπολογίσουμε μόνοι μας τα ματσαρίσματα από
`/api/requests` + `/api/listings`, αλλά θα χάναμε ακριβώς αυτό που μετράει: τη
**δική του κατάσταση** του CRM. Το «Νέο» είναι η λίστα εκκρεμοτήτων και αδειάζει
μόνη της όταν η γραμματεία δουλέψει μέσα στο CRM — καμία διπλή καταγραφή.

## Χρήση

```bash
node tools/crm-request-matchings.mjs                 # dry run — τυπώνει, δεν στέλνει
node tools/crm-request-matchings.mjs --send          # στέλνει το email
node tools/crm-request-matchings.mjs --request 135   # μόνο μία ζήτηση
```

Προϋπόθεση: ο Edge στο `:9222` **συνδεδεμένος στο CRM**. Αν έχει πέσει το
session, το script σταματά με μήνυμα αντί να στείλει άδειο digest.

Πρώτο live run (2026-07-27): 115 ενεργές ζητήσεις σαρώθηκαν σε ~2 λεπτά,
**14 ζητήσεις με 18 εκκρεμή «Νέα» ακίνητα**.

## Πότε τρέχει

**Βήμα 7 του `spitogatos-requests-fetch`, που η γραμματεία τρέχει κάθε πρωί.**
Κανένας scheduler — ο έλεγχος καβαλάει τη ρουτίνα που υπάρχει ήδη (απόφαση
Πάνου, 2026-07-27). Δουλεύει επειδή το digest σαρώνει **όλες** τις ενεργές
ζητήσεις, όχι μόνο όσες μόλις δημιουργήθηκαν: το πρωινό run του skill *είναι*
ο καθημερινός έλεγχος.

**Η παγίδα: το βήμα 7 πρέπει να τρέχει και τις μέρες χωρίς νέα leads.** Δύο
πράγματα γεννούν ματσαρίσματα — νέα ζήτηση (που το intake φτιάχνει) και **νέο
ακίνητο που ματσάρει παλιές ζητήσεις**. Το δεύτερο δεν έχει καμία σχέση με τα
Spitogatos leads, δεν έχει δικό του trigger (το webhook ακινήτων το παίρνει ο
Worker, που δεν φτάνει το session endpoint) και με 115 ενεργές ζητήσεις να
κάθονται είναι ο βασικός όγκος. Ένα «σήμερα δεν είχαμε leads → τέλος» θα
άφηνε τη γραμματεία τυφλή ακριβώς εκεί — γι' αυτό το SKILL.md το σημειώνει ως
υποχρεωτικό βήμα, ανεξάρτητο από το αποτέλεσμα των βημάτων 1–6.

Το digest είναι **stateless**: κάθε φορά στέλνει ό,τι είναι εκείνη τη στιγμή
«Νέο». Δεν κρατάμε τοπικά τι έχει ήδη αναφερθεί, οπότε τίποτα δεν χάνεται αν ένα
email αγνοηθεί — απλώς ξαναεμφανίζεται.

**Σιωπή ≠ επιτυχία.** Όταν δεν υπάρχει τίποτα «Νέο» δεν στέλνεται email, οπότε
ένα σπασμένο run θα έμοιαζε με ήσυχη μέρα. Δύο δικλείδες:

- Αν **>25% των σαρώσεων αποτύχει** (τυπικά: έληξε το session και το CRM
  γυρίζει τη σελίδα login αντί για JSON), το script **σκάει με exit 1** αντί να
  αναφέρει ψευδώς «καμία εκκρεμότητα».
- Αν αποτύχουν λιγότερες, το email το λέει καθαρά επάνω-επάνω («η λίστα μπορεί
  να είναι ελλιπής») — δεν σιωπά για ό,τι δεν κοίταξε.

Το βήμα 8 του skill αναφέρει το αποτέλεσμα του digest στον Πάνο, οπότε μια
αποτυχία φαίνεται και στο report του πρωινού run.

## Make

| | |
|---|---|
| Scenario | **CRM - Νέα ακίνητα σε ζητήσεις** (`6722234`) |
| Hook | `CRM — νέα ακίνητα σε ζητήσεις` (`3457244`) |
| Secret | `MAKE_MATCHINGS_WEBHOOK` στο `.dev.vars` — το URL είναι το ίδιο το credential |

Δύο modules, ίδιο μοτίβο με το [request-closed.md](request-closed.md): webhook →
Zoho mail. **Το HTML του email το φτιάχνει το script**, όχι το Make — η λίστα
έχει μεταβλητό μήκος και το mapping του Make για τέτοια είναι βασανιστήριο.
Το Make παίρνει `{subject, html}` και τα προωθεί. Δικό του scenario (όχι κλάδος
του contact form) για ξεχωριστό blast radius· DLQ ON.

## Ό,τι δεν έγινε

- **Σήμανση ως «Προτεινόμενα» από το script.** Το κουμπί στο tab καλεί
  `proposeWithoutEmail()` — δεν το έχουμε οδηγήσει headless. Σκόπιμα: η κρίση
  ποιο ακίνητο αξίζει να προταθεί είναι ανθρώπινη.
- **Trigger από νέο ακίνητο.** Θα ήθελε τον Worker να σηκώνει σημαία και τον
  τοπικό runner να τη διαβάζει· το πρωινό run το καλύπτει φθηνότερα.
